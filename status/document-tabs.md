# Вкладки документов (D134)

План по итогам обсуждения сложности с автором 2026-11-23. Решение D134 принято давно, D161
называл вкладки следующим шагом; здесь — уточнённые решения, срезы и рамки. Реализации ещё нет.

## Текущее состояние (по коду)

- `Viewer` — монолит ~90 полей, `app.rs` 12,4 тыс. строк, `impl Viewer` в 5 файлах (app.rs + 4
  формы). Глобальное для приложения и состояние одного документа вперемешку.
- Один воркер-поток с одной `Session` (`worker`, app.rs:460): канал запросов → канал моделей,
  сворачивание накопленных запросов. Функция самодостаточна.
- MCP — отдельный процесс (`datum mcp`, своя сессия), живой связи с окном нет; вотчер файлов
  отсутствует. Стыковка D161 — панели одной модели, не документы. Таблицы — отдельные окна ОС
  (D178), память окон — D293.

## Решения (автор, 2026-11-23)

1. **UI**: полоса вкладок над рабочей областью (браузер/VS Code). Стыковка панелей D161 общая;
   документы в стыковку не смешиваются; вынос вкладки на второй монитор — позже (совместимо с
   viewports).
2. **Воркер**: поток на вкладку (своя `Session` и кэш мешей); закрытие вкладки — обрыв канала,
   поток завершается сам. Пул не вводим.
3. **Состояние**: `Viewer { docs: Vec<Document>, … }` — ~25 глобальных полей остаются, ~40
   документных уходят в `Document` целиком. Ленивое выбрасывание состояния фоновых вкладок — нет
   (D134: состояние эскиза живёт у вкладки).
4. **MCP**: без изменений. Мост окна и `datum mcp` (активная вкладка, подсветка в обе стороны,
   VISION §3) — отдельная задача и запись в журнал; обещание D134 про агента откладывается до
   моста.
5. **Файл изменился на диске**: минимум — без вотчера, проверка только при повторном открытии
   того же файла. При Open/сохранении помнить mtime+размер; повторный Open того же пути:
   вкладка чистая и файл новее — перезагрузить на месте; вкладка грязная — спросить.
6. **Выход с грязными вкладками**: сразу один диалог со списком вкладок (не последовательные
   вопросы).
7. **Проект**: глобальный, поведение D142 без изменений — в концепции все файлы из одного
   проекта, машин per-вкладку не вводим.
8. **Таблицы** (автор, 2026-11-23): окна таблиц принадлежат открывшей их вкладке (активной в
   момент открытия) и закрываются вместе с ней. Переключение вкладок не перенаправляет уже
   открытые окна: таблица параметров продолжает показывать свою модель, пока её вкладка жива.
   Материалы, правила, инструменты и пресеты — контент глобальный (библиотека проекта, с вкладки
   не зависит), но время жизни окна — за вкладкой. Закрытие последней вкладки оставляет пустое
   окно (как «Close» сегодня); таблиц больше нет — их владелец закрыт.
9. **PERSPECTIVE** камеры: глобальная настройка по умолчанию.

Вне рамок: восстановление вкладок при следующем запуске (D134); drag-reorder вкладок;
параметр документа в командах MCP (до сборок); mixing документов в стыковке.

## Срезы

### 1. Расщепление Viewer без изменения поведения
- [x] Перенести документные поля в `Document` (пара каналов, модель, камера, fitted/turn,
  эскиз и entering, дерево, edits/offsets, формы в работе: flange/revolve/trim/rib/
  edge_finish/metadata/loft/mirror/extrusion и их черновики, picking/under/toggling/contour,
  flat, table, path, part/material/next_rule, viewport/sketch_rect/blank_fitted, hold).
  Глобальные остаются (keys/language/theme/i18n/settings, недавние и проект, библиотека и
  её фильтры, уроки и playing, native_windows, рендерер/adapter/статистика, dock, side_bar,
  quitting, shown/maximized, update). Осторожно с пограничными: `modes` эскиза (D167) —
  глобальная привычка; `library_due` — по потребителю.
- [x] Узкая передача i18n/keys аргументами при borrow-конфликтах; `Viewer { doc: Document }`,
  один документ, поведение то же. (Конфликтов не возникло: методы остались в `impl Viewer`,
  деструктуризация не понадобилась.)
- [x] `scripts/check.sh` зелёный, снимки egui_kittest не меняются. (427 + 9 тестов, свой
  повторный прогон архитектором, попарная сверка нормализованного diff — изменений логики нет.)

### 2. Механика нескольких документов (в UI всё ещё одна)
- [x] `docs: Vec<Document>` + `active`; воркер-поток на документ (`Document::spawn`: каналы,
  поток, первый `Request::Open`), дренирование всех каналов каждый кадр (`receive`/`took`,
  оконные последствия — только активному); точка «изменено» обновляется у каждого своего.
- [x] Закрытие документа: обрыв канала, поток завершается; `Request::Open`/`Request::Close`
  в потоке сохранены (вкладка = жизнь потока — включится срезом 3).
- [x] Поведение то же: одновременно существует один документ. (Инвариант среза 2; в тестах
  `h.state_mut().docs[0]` — обновить в срезе 3.)

### 3. Полоса вкладок и правила
- [ ] Полоса: имя/путь, точка «изменено», ×, закрытие средней кнопкой, Ctrl+Tab /
  Ctrl+Shift+Tab; заголовок окна за активной вкладкой.
- [ ] `file.new`/`file.open`/недавние открывают новую вкладку; Ctrl+W — закрыть вкладку (последняя
  закрытая оставляет пустое окно, как «Close» сегодня); повторное открытие того же файла —
  переход на его вкладку: канонизация пути, при расхождении mtime/размер решение 5.
- [ ] Выход и закрытие окна с грязными вкладками — один диалог со списком (решение 6).
- [ ] Реестр действий D131: `view.next_tab`, `view.previous_tab`; строки i18n.
- [ ] Тесты: правила фокуса, перезагрузки и точки — unit; снимки kittest переразрешить.

### 4. Кромки
- [ ] Таблицы: окно таблицы принадлежит открывшей его вкладке и закрывается вместе с ней
  (решение 8); переключение вкладок не перенаправляет открытые окна.
- [ ] Уроки: урок ведёт активную вкладку; проверить смену вкладки во время урока.
- [ ] Замер памяти фоновых вкладок на тяжёлой модели (10 000 отверстий) в 2–3 вкладках;
  при заметном росте — запись в журнал и решение (вытеснение кэша мешей фоновых).
- [ ] `scripts/check.sh` + `scripts/win-build.sh <ветка> --test`, ручная проверка автора в
  Windows.

## Открытые вопросы

- **Мост MCP ↔ окно** — отдельная задача (решение 4), приоритет назначит автор.

## Оценка и риски

- 3–5 рабочих дней «реализация + ревью» серией срезов; ядро, формат модели, эталоны и
  закреплённые хеши не трогаются, работа целиком в `datum-view`.
- Риски: тонкая классификация полей (список пограничных в срезе 1); память фоновых вкладок;
  объём ревью среза 1 — лечится срезом «без изменения поведения» и зелёными проверками.
