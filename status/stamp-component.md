## 1. Контракт двух эскизов

- [x] Геометрию элемента задаёт пара эскизов (D274). В актуальном `жалюзи2.json` `sketch1` лежит в XY, `sketch2` — в XZ с общей осью X, с живыми проекциями `p9` → `v1`, `p8` → `v2`. Текущий CLI строит оба эскиза.
- [x] Роли «Рез / Переход» — отдельные метаданные рабочих кривых, не значение `construction` (D275). Вспомогательная ось сама по себе не становится частью штампа. Для дополнительных свойств не вводим новые типы примитивов.
- [x] Автор разметил `жалюзи2.json`: в `sketch2` `l1/l4` — `cut`, `a1/a2/l2/l5` — `transition`; `l3` — вспомогательная ось зеркала без роли. В `sketch1` дуга `a1` и касательный к ней отрезок `l1` не имеют ролей; отрезок вспомогательный. Имена указаны в пределах своих эскизов.
- [x] Автор подтвердил чтение жалюзи: `sketch1` — полное сечение в середине, включая вспомогательный `l1`; `sketch2` — след границы на исходной плоскости листа. К дугам `transition` сечение теряет подъём и на дугах металл возвращается в плоскость листа без разрыва (D278).
- [x] Второй пример автора `язык.json` строится: `sketch1` — сечение XZ (подъём 3 мм, полка 5 мм, носик 5 мм под 15°), `sketch2` — контур в XY. `l1/l5` — `transition` у корня; `l2/l3/l6/l7/a1/a2` — `cut` по бокам и у носика; `l4` — ось. Назначение — язык крышки, входящий в отдельный паз (D257/D278).
- [x] D279: первый эскиз задаёт форму сечения, второй её уточняет: след границы, резы, переходы и очертания в плане. У языка вертикаль у корня — настоящая стенка; дуги `a1/a2` второго эскиза обрезают поднятый носик, а не сводят его к листу. У жалюзи переход вдоль концевых дуг, в отличие от носика языка, возвращается к листу.
- [x] D280: первый эскиз задаёт одну опорную поверхность целиком — наружную по умолчанию или внутреннюю по явному свойству сечения. При смене толщины сохраняется заданный профиль, вторую сторону строим в сторону материала на толщину из правила; нейтральный слой в первом срезе не вводим.
- [x] D281: углы остаются как нарисованы; Datum не подставляет радиус из правила. Скругление — задаваемая конструктором явная операция в поддереве элемента, не условие первого результата. Дуги в существующих эскизах не удаляем и не игнорируем.
- [x] D282: `cut` в виде сверху задаёт границы, которые режутся; DXF получает настоящие резы после учёта развёрнутой формы. `transition` не режется. Проекция второго эскиза не выдаётся за рез заготовки.

## 4. Язык без скруглений: первый сквозной результат

Эталон `tests/models/stamp-tongue-straight.json` с пластиной, постановкой,
сшитым телом и узлом `unfold`. Первая постановка поддержана на выпуклой
четырёхугольной пластине с прямолинейными границами без отверстий (D292).

По D289 сначала выполняется рез по одной линии, затем формовка. Второй
настраиваемый режим — рез самим штампом при формовке. Радиусы задаются в
эскизах и применяются явным скруглением в поддереве. Первый 3D-эталон
сохраняет острые изломы. По D290 размер окна в 3D-стенке совпадает с размером
развёрнутого языка. Этот же контур задаёт линию предварительного реза.
Для острого эталона длину развёрнутого сечения определяет D291: площадь
сечения поднятого материала делится на толщину листа, металл у корня
учитывается один раз.

- [ ] Сделать отдельный эталон по `язык.json` с тем же трёхзвенным сечением (стенка, полка, наклонный носик), но прямолинейной границей в плане. Исходник автора не править. Протянуть сечение по ширине и подрезать по границе. На опорной стороне сохранить профиль; вторую построить на толщину из правила, на каждом участке по его нормали, а у излома плоских участков состыковать смещённые плоскости. Проверить локальную привязку обеих сторон листа, переворот, две толщины и отказ при схлопывании или самопересечении. Пока только плоская стенка и аналитически проверяемые участки.
- [ ] В стенке оставляется окно по D290, стороны сшиваются у корня. Проверены валидность тела, объём, тесселяция, STEP, выход за край, отказ на пластине с отверстием, правка общего размера эскизов и смена правила листа. Осталось проверить сохранение ссылок при независимой правке двух эскизов. Поддержка стенок с гибами и существующими отверстиями требует отдельной валидации пересечений.
- [x] Вычислить длину плоского участка по D291 и перенести на него три кромки `cut`. Проверить баланс объёма после сшивки и открытый контур предварительного реза.
- [ ] Проверить, что развёрнутый язык и остальной лист дают совместимую заготовку: соответствующие стороны одного реза согласованы, нет наложения материала или удвоенного прохода; если требуется разгрузка или удаляемый участок, не генерировать его молча. Для допустимого открытого реза проверить применимость D235/D237 и политики `kerf`. При неизвестной развёртке или несовместимой заготовке DXF не выдавать. Проверить, что последующая операция не стирает штамп, а если перестроение наложения не поддержано — явно отказать. Не плодить второй тип листового результата рядом с `Formed` (D256).

## Предыстория и примеры

Автор раскритиковал результат D261 («гладкая капсула», не жалюзи: прорези не видно;
матрица — моё изобретение). Концепция переработана в диалоге, примеры автора лежат в
`C:\develop\datum-test\Детали\`:

- `жалюзи.json` — S-профиль (полный вид формы); текущий `язык.json` — сечение
  и размеченный след языка крышки, описанные в D278;
- `профиль.json` (штамп: выше оси x) и `профиль2.json` (отверстие-ответное: ниже оси) —
  Z-профили, возвращающиеся на горизонталь;
- `жалюзи2.json` (обновлён) — **контракт: штамп = 2 перпендикулярных эскиза, полностью
  определяющие геометрию**.

Текущий `жалюзи2.json`: обе плоскости пересекаются по X. По решённым точкам
`sketch1` идёт от `x=0` к `x≈8,17`, высота конца `≈1,33`; в `sketch2` резы
`l1/l4` лежат на `x≈8,17`, их внешние концы на продольных станциях `±25`,
а прямые переходы `l2/l5` — на `x=0`. Точки `v1` и `p8` сходятся по
симметрии, но это разные имена, без явного `coincident`: будущий обход не
должен молча склеивать концы по близким координатам. Оба эскиза вычисляются
и детерминированы; у каждого осталось по три степени свободы. Файл только
прочитан, способ построения 3D ещё не утверждён.

Правка ширины в `язык.json`: зеркало (D244) оставило ведущий размер `l1=10`,
скопировало `l5=10` и связало их `equal` и симметрией. На временной копии
`l1=5`, `l5=10` воспроизводит конфликт; удалить только размер `l5` и изменить
`l1` на 5 даёт полный размер 10 мм, на 2,5 — полный размер 5 мм, оба варианта
перестраиваются. Исходник не менялся. Это не ослабление решателя; поведение
зеркала с копиями управляющих размеров — отдельный вопрос от формы штампа.
После правки автора сохранённый файл с `l1=5` строится и даёт одинаковые
хеши эскизов на 1/4/16 потоках.

Прежнее прочтение `жалюзи2.json` было гипотезой: поперечное сечение и продольный
профиль концов, общий ориентир — ось высоты. Оно не определило поверхности между
сечениями, сторону толщины и смысл нижнего профиля. Нельзя считать контрактом
ни «штору» на торце, ни полуобороты, ни признак разрыва по высоте конца. Числа
в прежнем сохранённом примере расходились с ограничениями; эталон нужен решённый.

## Уроки, которые не потерять

- Отладочный приём: жёсткая проверка спеков дуг в `attach_curves` (концы на окружности,
  `at(u,sweep)` = v, sweep < π) + печать плоской развёртки падающей грани — находит
  «комплементарные» дуги и несогласованные домены за минуты.
- D261 — прежняя схема жалюзи, не основание для геометрии двух эскизов.
- Профиль лепестка не подтверждён; лепесток отложен (планировка point в операции уже
  реализована).
- Стиль работы с автором: обсуждать текстом (без ASCII-рисунков в консоли); рендеры — PNG
  в `/tmp/opencode` (для Windows `\\wsl.localhost\Ubuntu\tmp\opencode\`); таймбоксы по шагам
  (~1,5–2 ч), при перерасходе — стоп и обсуждение. Рендер через MCP держит старую сборку:
  рендерить из OBJ питон-скриптом (`/tmp/opencode/render.py`, `render2.py`).
