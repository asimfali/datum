## Обязательные проверки перед завершением задачи
`scripts/check.sh` (или скилл `/check`): fmt, clippy `-D warnings`, тесты, проверка детерминизма (с этапа M1). Список проверок живёт только в этом скрипте; его же запускает CI.

## Детерминизм (нарушение = баг)
- Не итерировать `HashMap`/`HashSet`, если порядок влияет на результат. Использовать `BTreeMap` или сортированные `Vec`.
- Результаты параллельных этапов собирать в индексированный `Vec`, затем сортировать по ключу.
- Не использовать `par_iter().sum()` для `f64`; редукции — с фиксированным порядком.
- Не использовать `DefaultHasher`; для идентификаторов и хешей — только `blake3`.
- `TopoId` выводится из происхождения элемента (см. ARCHITECTURE §4.2), никогда из счётчика.
- Математика с неточным результатом (`sin`, `cos`, `exp`…) — только через `libm`: системные библиотеки различаются между ОС.
- Закреплённые хеши (`tests/model-hashes.json`, хеш куба в `datum-brep`) меняются только осознанно (`DATUM_BLESS=1`), с причиной в сообщении коммита.

## Геометрия
- Решения «с какой стороны / пересекается ли» — только через точные предикаты (`robust`).
- Не вводить «магические» эпсилоны для сравнения координат. Если без допуска не обойтись — обсудить и записать решение в журнал.
- Неподдерживаемый вырожденный случай → `Err(Degenerate)`, а не приблизительный результат.
- В debug-сборке каждая операция вызывает `Body::validate()` на результате.

## Минимализм и DRY
- Мерило функционала — реальная польза для инженера-конструктора (см. ARCHITECTURE §1, «Долгосрочная цель»). Пишем только то, что нужно для текущего этапа (M0–M5) и критериев C1–C4. Никакого функционала «на будущее», точек расширения, конфигов и абстракций без второго реального потребителя.
- Один факт — одно место: формула, алгоритм, константа, структура живут в одном месте и переиспользуются. Дублирование логики — баг, его устраняют до завершения задачи.
- Абстракция (трейт, дженерик, слой) появляется, только когда без неё уже есть дублирование. Три похожие строки лучше преждевременного обобщения; третий повтор логики — сигнал выделить общее.
- Новая зависимость (крейт) — только если она решает задачу заметно лучше 50 строк своего кода. Минимум фич в `Cargo.toml`.
- Удалять мёртвый код, неиспользуемые параметры и закомментированные куски сразу, а не «потом».

## Производительность
- Оптимизация — требование, а не полировка. Горячие пути (булевы, BVH, тесселяция, хеш) проектируются под кэш и параллелизм с самого начала.
- Данные — плоские `Vec` с индексами (SoA, где это даёт выигрыш); без лишних `Box`/`Arc`/`clone` и аллокаций в циклах. Переиспользовать буферы, `with_capacity`, `SmallVec` для коротких списков.
- Любое утверждение «так быстрее» подтверждается бенчмарком (`criterion`) или профилем (`perf`/`flamegraph`). Регрессия в бенчмарке — повод не мержить.
- Детерминизм и корректность важнее скорости: оптимизация, нарушающая правила ниже, не принимается.

## Код
- `unsafe` — только с комментарием-обоснованием и с согласования.
- Тело (`Body`) неизменяемо после построения. Новые данные — новое тело.
- Каждая новая операция: unit-тесты, property-тест инвариантов (если применимо), эталонная модель в `tests/models/`.
- Бенчмарки — `criterion` в `benches/`, всегда с вариантами 1 поток / все потоки.
