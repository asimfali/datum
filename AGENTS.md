# AGENTS.md — правила проекта Datum

Перед любой работой прочитай `ARCHITECTURE.md` (цель, C1–C4, крейты, открытые вопросы). Тематические страницы и журнал D* открывай по оглавлению. `PAINS.md` — боли инженеров, `VISION.md` — как Datum работает с инженером и агентом: новые функции и приоритеты сверять с обоими.

## Язык
- Документация и обсуждение — на русском. Исключение: `README.md` на английском (лицо проекта для мирового сообщества, D17); `README.ru.md` — его русская версия, правятся вместе.
- Код, идентификаторы, комментарии в коде, сообщения коммитов — на английском.

## Поиск: сначала найти, потом читать
- Место в коде — инструмент `grep` (`path`, `include`, `limit`), имена файлов — `glob`; не заменять их `bash`-обходом: встроенный `grep` уважает `.gitignore`.
- Читать найденный диапазон (`read` с `offset`/`limit`); файл целиком — только если он и есть предмет задачи.
- `architecture/decisions.md` — журнал решений: запись ищется по номеру (`rg '^\| D258'`), свежие — с конца (`rg '^\| D' architecture/decisions.md | tail -n 20`), а не чтением всего файла.
- «Когда и почему появилось» — `git log -S'<символ>' --oneline`, `git blame -L`, `gh pr list --search '<слово>'`; историю файлов целиком не листать.
- Широкий вопрос «где это вообще используется» — субагенту `explore`, а не основной сессии.
- Вывод команды не печатать целиком: `-m N`, `| head -n 30`, `cargo test -p <крейт> <тест>` вместо всего набора.

## Цена контекста
- Всё, что грузится всегда (`AGENTS.md`, `HANDOFF.md`, скиллы, схемы MCP), платится на каждом шаге: потолок — 2k токенов на `AGENTS.md` и `HANDOFF.md`, 1k на скиллы; мерить `ctx-cost --cap 2000`.

## Команды пользователя
Скиллы `.claude/skills/`: «проверка» → `win-build`, «Обнови» → `update-main`, «PR» → `pr`, «релиз» → `release`.

## Обязательные проверки перед завершением задачи
`scripts/check.sh` (или скилл `/check`): fmt, clippy `-D warnings`, тесты, проверка детерминизма (с этапа M1). Список проверок живёт только в этом скрипте; его же запускает CI.

## Детерминизм (нарушение = баг)
- Не итерировать `HashMap`/`HashSet`, если порядок влияет на результат. Использовать `BTreeMap` или сортированные `Vec`.
- Результаты параллельных этапов собирать в индексированный `Vec`, затем сортировать по ключу.
- Не использовать `par_iter().sum()` для `f64`; редукции — с фиксированным порядком.
- Не использовать `DefaultHasher`; для идентификаторов и хешей — только `blake3`.
- `TopoId` выводится из происхождения элемента (см. `architecture/kernel.md`, §4.2), никогда из счётчика.
- Математика с неточным результатом (`sin`, `cos`, `exp`…) — только через `libm`: системные библиотеки различаются между ОС.
- Закреплённые хеши (`tests/model-hashes.json`, хеш куба в `datum-brep`) меняются только осознанно (`DATUM_BLESS=1`), с причиной в сообщении коммита.

## Геометрия
- Решения «с какой стороны / пересекается ли» — только через точные предикаты (`robust`).
- Не вводить «магические» эпсилоны для сравнения координат: без допуска не обойтись — обсудить и записать решение в журнал.
- Неподдерживаемый вырожденный случай → `Err(Degenerate)`, а не приблизительный результат.
- В debug-сборке каждая операция вызывает `Body::validate()` на результате.

## Минимализм и DRY
- Реализуем полезное инженеру на текущем этапе M0–M5 по C1–C4 (ARCHITECTURE §1). Расширения, настройки и абстракции требуют второго реального потребителя.
- Формулы, алгоритмы, константы и структуры храним в одном месте. Устраняем дублирование логики в этой же задаче. Трейты и слои обобщают существующих потребителей.
- Новая зависимость (крейт) — только если она решает задачу заметно лучше 50 строк своего кода. Минимум фич в `Cargo.toml`.
- Удалять мёртвый код, неиспользуемые параметры и закомментированные куски сразу, а не «потом».

## Производительность
- Оптимизация — требование, а не полировка. Горячие пути (булевы, BVH, тесселяция, хеш) проектируются под кэш и параллелизм с самого начала.
- Данные — плоские `Vec` с индексами (SoA, где это даёт выигрыш); без лишних `Box`/`Arc`/`clone` и аллокаций в циклах. Переиспользовать буферы, `with_capacity`, `SmallVec` для коротких списков.
- Любое утверждение «так быстрее» подтверждается бенчмарком (`criterion`) или профилем (`perf`/`flamegraph`). Регрессия в бенчмарке — повод не мержить.
- Детерминизм и корректность важнее скорости.

## Код
- `unsafe` — только с комментарием-обоснованием и с согласования.
- Тело (`Body`) неизменяемо после построения. Новые данные — новое тело.
- Каждая новая операция: unit-тесты, property-тест инвариантов (если применимо), эталонная модель в `tests/models/`.
- Бенчмарки — `criterion` в `benches/`, всегда с вариантами 1 поток / все потоки.

## Распределение работы между моделями
- Перед задачей оценить её и разбить на участки. Решения (журнал, архитектура, спорные места) и разбор причин ошибок — основная сессия делает сама.
- Простые участки с ясным описанием — субагентам: функции по готовому описанию (что сделать, файлы, тесты, что считать готовым), механическое (тексты, переводы, документация) — младшей модели.
- Основная сессия проверяет каждый diff, запускает `scripts/check.sh`, отвечает автору, делает коммиты и PR. Слияние — только автором; агентам запрещено автослияние, включая релизы.
- Релиз завершён после публикации. Архивы скачивать и проверять только по просьбе автора.
- Параллельные субагенты не трогают одни файлы; в одном дереве — последовательно или на непересекающихся крейтах.

## Документация и память между задачами
- Значимое решение → «Журнал решений» `architecture/decisions.md`, закрытый вопрос (Q*) — туда же с выводом; в конце задачи обновляй `HANDOFF.md` (цель, состояние, следующий шаг, паузы, файлы, проверки).
- Планы — `ROADMAP.md` или `status/`, чат не источник истины. Планы `status/` читать через `python3 scripts/status_summary.py` (`overview`/`next`/`done`/`plan`), а не целиком. Машины чат друг друга не видят: связь — комментарии в GitHub issue (#248).
