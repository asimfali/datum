# Архитектура: параллельное геометрическое ядро (PoC)

> **Datum** — Design Automation Toolkit for Universal Modeling (технически: Distributed Architecture for Topology-based Unified Modeling).
> Статус: черновик v0.21, 2026-10-20. Документ живой: каждое значимое решение фиксируется в разделе «Журнал решений».

## 1. Цель

Доказать, что параметрическое твердотельное ядро уровня Inventor можно построить так, чтобы оно **использовало все ядра процессора** и при этом оставалось **детерминированным**.

Это proof of concept, а не продукт. Сложные и вырожденные геометрические случаи сознательно вынесены за рамки (см. раздел 10).

### Долгосрочная цель

Если концепция подтвердится, PoC станет основой **открытого 3D CAD для профессионалов**: инженеров и конструкторов. Мерило каждой функции — реальная польза в ежедневной инженерной работе, а не список фич для маркетинга. Коммерческие системы (Inventor, SolidWorks, CATIA) давно наращивают второстепенное и не решают базовые проблемы: медленный однопоточный пересчёт, потерянные ссылки при правке истории, непредсказуемые сбои перестроения.

Что из этого следует уже для PoC:
- скорость отклика и надёжность перестроения — это функции для пользователя, а не технические детали;
- стабильные ссылки на топологию (§4.2) — ответ на одну из главных болей конструктора;
- приоритеты после PoC задают реальные сценарии работы инженеров, а не паритет с коммерческими CAD.

### Что доказываем (критерии успеха)

| # | Утверждение | Как меряем |
|---|---|---|
| C1 | Пересчёт графа операций масштабируется по ядрам на «широких» моделях | Бенчмарк: N независимых тел и операций в одном графе; время на 1/2/4/8/16 потоках |
| C2 | Правка параметра в конце длинной истории пересчитывается мгновенно | Бенчмарк: цепочка из 200 операций, правка последней; цель < 10 мс сверх стоимости самой операции |
| C3 | Булева операция ускоряется внутри себя | Эталоны из практики (PAINS): **пластина с 10 000 отверстий** (P4) и **рельеф + котлован → объём выемки** (P9), 10k–1M граней; время по числу потоков |
| C4 | Результат побитово одинаков при любом числе потоков | Тест: канонический хеш тела при `RAYON_NUM_THREADS=1,4,16` |

Сравнение всегда внутри нашего движка: последовательный режим против параллельного.

## 2. Принципы

1. **Неизменяемость.** Тело (`Body`) после построения не меняется. Операция создаёт новое тело. Неизменённые части (геометрия поверхностей, кривых) разделяются через `Arc`.
2. **Явные зависимости.** Модель — ориентированный ациклический граф (DAG), а не линейный список. Всё, от чего зависит операция, видно в её входах.
3. **Детерминизм прежде скорости.** Параллельный код обязан давать тот же результат, что и последовательный, бит в бит.
4. **Символьная идентичность вместо допусков.** Где возможно, совпадение элементов определяется по их происхождению (ключу), а не по близости координат.
5. **Честный отказ.** Если операция встретила неподдерживаемый (вырожденный) случай, она возвращает ошибку `Degenerate`, а не «примерно правильное» тело.
6. **Ядро без UI.** Геометрия и граф не зависят от интерфейса. Просмотр, CLI и интеграция с CADCraft — отдельные потребители.
7. **Минимализм.** Пишем только то, что нужно текущему этапу и критериям C1–C4. Стоимость операции пропорциональна изменению, а не размеру тела, везде, где это достижимо без усложнения (§4.1, §5.1).
8. **Нет абсолютных допусков — нет рабочей области.** Ограничение «модель в кубе 1 км» (Parasolid; у Revit — 20 миль) — следствие абсолютного линейного допуска. У нас решения принимают точные предикаты, совпадение определяется по символьным ключам, погрешность построений `f64` относительная. Поэтому ядро не зависит от масштаба: генплан на 10 км и болт M6 живут в одной модели (§4.3, PAINS P8).
9. **Нет закрытых API.** Встроенные предметные модули (провода, трубы, листовой металл, стандарты) строятся на том же публичном командном слое (§6), что доступен пользователю и надстройкам. Нет внутренних возможностей, недоступных снаружи: если встроенный модуль плох, инженер пишет свой с теми же правами (PAINS P2, P10).

## 3. Структура крейтов

```
datum/
├─ crates/
│  ├─ datum-math      векторы, матрицы, точные предикаты (orient2d/orient3d), BVH
│  ├─ datum-brep      неизменяемый B-rep: Body, топология half-edge, TopoId, проверки, хеш
│  ├─ datum-ops       операции: примитивы, выдавливание, булевы, массивы
│  ├─ datum-graph     граф операций, мемоизация, инкрементальный пересчёт, планировщик
│  ├─ datum-sketch    2D-эскиз и решатель ограничений
│  ├─ datum-tess      тесселяция, экспорт STL/OBJ
│  ├─ datum-model     формат файла (JSON) ↔ граф (M1b); реестр команд, запросы топологии (M1c, §6)
│  ├─ datum-mcp       MCP-сервер: JSON-RPC 2.0 через stdio поверх реестра команд (§6)
│  └─ datum-view      просмотрщик (egui + wgpu), появляется на этапе M4
├─ apps/
│  └─ datum-cli       build / bench / export / determinism-check
├─ benches/        criterion
└─ tests/          интеграционные и property-based тесты, эталонные модели
```

Правило зависимостей: `math ← brep ← ops ← graph ← model ← cli/mcp/view`.

Это целевая структура, а не стартовая. На M0 создаются только `datum-math`, `datum-brep` и `datum-cli`. Крейт выделяется, когда у него появляется содержимое (обычно на этапе, который его вводит). `datum-model` и `datum-mcp` появляются на M1. `serde_json` подключают только `model`, `mcp` и `cli`; в `ops`/`graph` типы параметров имеют лишь `derive(Serialize, Deserialize, JsonSchema)`. `sketch` зависит только от `math`. Обратных зависимостей нет.

## 4. Ключевые структуры данных

### 4.1 Тело (datum-brep)

Топология хранится на индексах внутри тела (без `Rc`-циклов, дружелюбно к borrow checker и к кэшу).

```rust
pub struct TopoId(pub u128);          // стабильный идентификатор, см. 4.2

pub struct Body {
    vertices:   Vec<Vertex>,          // TopoId + точка
    half_edges: Vec<HalfEdge>,        // origin, twin, loop, edge; next не хранится (см. ниже)
    edges:      Vec<Edge>,            // TopoId + полуребро от вершины с меньшим TopoId
    loops:      Vec<Loop>,            // грань + непрерывный диапазон полурёбер
    faces:      Vec<Face>,            // TopoId, плоскость, диапазон циклов (внешний первым), hash
    hash:       [u8; 32],             // хеш Меркла по хешам граней, см. ниже
}

pub type BodyRef = Arc<Body>;
```

- Поверхность грани — плоскость, цилиндр (M5a, D65) или стенка выреза в свальцованном листе (M5c, D68); ребро — отрезок, дуга окружности или кусок развёртки на заданном радиусе (поле `curve` ребра, индекс в `Body::curves`).
- **Непрерывные диапазоны вместо указателей.** Полурёбра цикла лежат подряд, циклы грани — подряд, поэтому `next` вычисляется из индекса и не хранится. Оболочки (shells) не хранятся: связные компоненты считаются при проверке; отдельная структура появится, когда операция будет в ней нуждаться (M2).
- Единственный конструктор тела — `build(vertices, faces)`: принимает вершины и грани по `TopoId` в любом порядке и строит канонический вид. `TopoId` ребра — хеш `TopoId` двух его вершин.
- **Хеш Меркла.** Каждая грань хранит свой хеш: `TopoId`, поверхность, координаты и `TopoId` вершин и рёбер её циклов в каноническом порядке. Индексы внутри тела в хеш не входят, поэтому хеш грани не меняется при переносе в другое тело. `content_hash` тела — blake3 от последовательности хешей граней в порядке `TopoId`. Нетронутые операцией грани переносятся с готовым хешем. Пересчитываются только новые и изменённые грани, а сводка по 32-байтным хешам дешёвая (100k граней ≈ 3 МБ).
- **Слияние вместо сортировки.** Нетронутые элементы приходят из входного тела уже отсортированными, новых обычно немного. Сортируем только новые, затем сливаем за O(n) с перенумерацией индексов. Полная сортировка O(n log n) на каждую операцию не нужна.
- **Грани с тысячами циклов.** Отдельного индекса циклов нет (D44): булева операция видит грань через её триангуляцию (D38) и широкую фазу, а триангуляция — заметание с разбиением на монотонные части, O(n log n) по числу вершин грани. Перфорация не даёт O(N²) (PAINS P4).
- Копирование векторов при каждой операции (O(n), по сути memcpy) пока принимаем. Персистентные или постраничные структуры вводим, только если бенчмарк C2 покажет, что узкое место именно здесь.
- Порядок элементов в векторах **канонический**: отсортирован по `TopoId` в конце каждой операции. Поэтому одинаковое тело всегда имеет одинаковое представление в памяти и одинаковый хеш.
- `Body::validate()` проверяет: замкнутость, многообразность, согласованность half-edge, формулу Эйлера, ориентацию (объём > 0).

### 4.2 Стабильные идентификаторы (TopoId)

Решение проблемы топологического именования и одновременно основа детерминизма.

`TopoId` — хеш **происхождения** элемента, а не счётчик и не адрес в памяти:

| Элемент | Происхождение |
|---|---|
| Боковая грань выдавливания | `hash(feature_id, "side", sketch_edge_id)` |
| Торцы выдавливания | `hash(feature_id, "cap_start" / "cap_end")`; у профиля из нескольких областей — ещё и точка, с которой начинается внешний контур области |
| Грань после булевой, не разрезана | исходный `TopoId` |
| Кусок разрезанной грани | единственный кусок сохраняет `TopoId` грани (отверстие не меняет ссылку на грань); если кусков несколько — `hash("boolean.split", parent_face, наименьший TopoId вершины внешнего цикла)` |
| Элемент инструмента булевой | `hash("boolean.tool", feature_id, k, source_id)`, `k` — номер входа: одно тело может быть несколькими инструментами |
| Вершина пересечения | `hash("x", edge_id, face_id)` — см. 7.2 |
| Копия массива `pattern_grid` | `hash("pattern.copy", feature_id, i, j, source_id)`: номер копии — пара `(i, j)`, поэтому новые ряды и столбцы не переименовывают существующие копии |

Хеш — `blake3` (стабилен между запусками и платформами). `std::collections::hash_map::DefaultHasher` запрещён: он рандомизирован.

Ссылки на топологию (например, «вырез на грани X») хранятся как `TopoId`. Если после перестроения элемента нет, это явная ошибка `LostReference`, а не тихая подмена.

### 4.3 Масштаб: системы координат, геопривязка, отображение

- **Локальные системы координат.** Тело хранит геометрию в своей системе, рядом с нулём. Размещение — жёсткое преобразование `f64` на уровне вхождения; одно тело может иметь много вхождений (массивы, перфорация, крепёж). Мировые координаты — цепочка преобразований, как в сборке.
- **Геопривязка.** Верхний уровень модели может нести систему координат проекта (МСК, UTM): геодезические координаты не попадают внутрь геометрии и не съедают значащие цифры.
- **Отображение (M4):**
  - отрисовка относительно камеры: позиция камеры вычитается в `f64` до передачи в GPU (`f32`), поэтому вдали от нуля ничего не дрожит;
  - тесселяция по экранной погрешности, а не по абсолютной хорде;
  - уровни детализации **как в картах**: иерархия по BVH сцены; объект, проекция которого на экран меньше порога, не отрисовывается и не тесселируется, пока к нему не приблизятся. Тесселяции кэшируются по `(content_hash, уровень)`.
- Отображение никогда не влияет на модель: уровни детализации — только для экрана, расчёты (объём, булевы, экспорт) всегда по полной геометрии.

### 4.4 Граф операций (datum-ops, datum-graph)

```rust
// datum-ops: закрытый набор операций; новая операция — новый вариант (D31)
pub enum Op {
    Prism { polygon: Vec<Vec2>, z0: f64, z1: f64 },          // 0 входов
    Transform { translate: Vec3, axis: Vec3, angle_deg: f64 }, // 1 вход
    Boolean { kind: BooleanKind, through: Option<Vec3> },      // цель + ≥ 1 инструментов
    PatternGrid { count: [u32; 2], step: [Vec3; 2] },          // 1 вход
    Terrain { origin, step, count, heights, base },            // 0 входов
    Sketch { sketch, plane: Option<SketchPlane>, face: Option<String> }, // 0 или 1 вход (тело с гранью)
    Extrude { z0: f64, z1: f64 },                              // 1 вход: эскиз
}
pub enum Value { Body(Body), Sketch(Placed) }                  // значение узла
impl Op {
    fn arity(&self) -> RangeInclusive<usize>;
    fn hash_params(&self, h: &mut blake3::Hasher);          // f64 — через to_bits
    fn eval(&self, feature: TopoId, inputs: &[&Body]) -> Result<Body, BrepError>;
}

// datum-graph
pub struct Node {
    name: String,          // уникальное имя в модели
    id: TopoId,            // hash("feature", name): переживает правки и перестановки
    op: Op,
    inputs: Vec<NodeIx>,   // всегда раньше узла: граф ацикличен по построению
}
```

- `Op::eval` — единственное место, где в debug-сборке вызывается `Body::validate()` для результата любой операции.
- Значение узла — `Arc<Value>`: тело или размещённый эскиз (D56). Ключ кэша берёт `content_hash` значения входа: у эскиза — хеш системы координат, решённых точек и отрезков.

## 5. Вычисление графа

### 5.1 Инкрементальность и мемоизация

Ключ кэша узла: `hash(TopoId узла, тип и параметры операции, content_hash всех входов)`. `TopoId` узла входит в ключ, потому что от него выводятся `TopoId` элементов тела.

- Изменился параметр → меняется ключ узла → узел пересчитывается.
- **Ранняя отсечка:** если после пересчёта `content_hash` результата совпал с прежним, узлы ниже не пересчитываются.
- Кэш — по ключу, поэтому undo/redo и «вернуть старое значение» попадают в кэш бесплатно. Политика вытеснения — LRU по памяти (позже; сейчас кэш не ограничен).
- Ошибки не кэшируются: упавший узел пересчитывается при следующем вычислении.

### 5.2 Планировщик

- Пометки «грязных» узлов нет (D32): каждое вычисление обходит весь граф и берёт тела из кэша по ключу. Изменённые узлы и всё, что ниже, получают новые ключи сами; ранняя отсечка выходит бесплатно. Обход 200 узлов — около 0,1 мс.
- Выполнение в `rayon::scope`: у каждого узла атомарный счётчик неготовых входов; узел запускается, как только счётчик дошёл до нуля. Из готовых зависимых один выполняется тем же потоком, остальные уходят в пул: цепочка не прыгает между ядрами.
- Упавший узел даёт `EvalError::Op`, его зависимые — `EvalError::Input(имя)`: причина видна по цепочке.
- Внутри узла операции сами используют `par_iter`. Вложенный параллелизм rayon балансирует через work stealing.
- Последовательный режим (`--threads 1`) — тот же код с пулом на один поток, никакой отдельной ветки.

## 6. Командный слой: JSON и MCP

JSON — родной язык ядра для всего, что приходит снаружи. MCP — тонкий транспорт поверх него. Геометрия (`math`, `brep`) о JSON и MCP не знает.

### 6.1 Один тип — четыре потребителя

Параметры каждой операции (`Feature`) — serde-структура с `schemars::JsonSchema`. Один и тот же тип служит:
1. параметрами узла графа;
2. записью в файле модели;
3. аргументами MCP-команды (схема генерируется из типа, а не пишется руками);
4. формой в интерфейсе (M4).

Реестр команд один. CLI, MCP и будущий UI вызывают одни и те же команды (как в CADCraft: `execute` + `list_commands`).

### 6.2 Формат файла

- В файле хранится **граф операций**, а не B-rep. Тело — производные данные: детерминизм гарантирует побитово то же тело при перестроении.
- Канонический JSON: стабильный порядок ключей, форматированный вывод (осмысленный diff в git, стабильный хеш файла).
- `f64` — с `serde_json/float_roundtrip`: значение после сохранения и чтения совпадает бит в бит. Без этого ломаются детерминизм и ключи кэша.
- Поле `"format": "datum/1"` с первого файла: основа для миграций.
- Операции идут в порядке истории; вход — по имени более ранней операции. Операция — плоский объект: `name`, `inputs`, `op` и параметры операции; неизвестные поля — ошибка с указанием операции.
- Параметры модели — раздел `"parameters": {"w": 120, "h": "w / 2"}`; размеры эскиза и числа операций (высоты выдавливания и призмы, сдвиг и угол переноса, число копий и шаг массива) — число или выражение параметров (D57).

```json
{
  "format": "datum/1",
  "features": [
    { "name": "profile", "op": "prism", "polygon": [[0, 0], [60, 0], [60, 5], [0, 5]], "z0": 0, "z1": 30 },
    { "name": "right", "op": "transform", "inputs": ["profile"], "translate": [80, 0, 0], "angle_deg": 90 }
  ]
}
```
- Не в JSON: кэш B-rep, тесселяция, импортированная геометрия без истории (будущий STEP). Позже — бинарные данные рядом, адресуемые по `content_hash`, возможно в zip-контейнере (как 3MF). В PoC не делается.

### 6.3 MCP

`datum-mcp`: JSON-RPC 2.0 через stdio, без SDK, по образцу `cadcraft-mcp`. Запуск — `datum mcp`; в репозитории `.mcp.json` подключает его к Claude Code. Сейчас один бэкенд — сессия в процессе (`Session` из `datum-model`); `Remote` к запущенному приложению появится с `datum-view` (M4).

Реестр команд — таблица в `datum-model::Session`: имя, описание, схема параметров, обработчик. Команды: `new`, `open`, `save`, `add`, `set_parameter`, `remove_parameter`, `edit` (частичная: только меняемые поля), `remove` (только неиспользуемой операции), `inspect` (с вычисленными параметрами), `mass_properties`, `query_faces`. Каждая правка пересчитывает модель и возвращает сводку: сколько пересчитано, сколько взято из кэша, что упало и почему. Инструменты MCP — `execute`, `list_commands` и именованные запросы; их схемы берутся из реестра.

| Инструмент | Назначение | Статус |
|---|---|---|

| Инструмент | Назначение |
|---|---|
| `execute` / `list_commands` | любая команда с JSON-параметрами; описание команд со схемами | M1 |
| `inspect_model` | граф операций, тела, статус перестроения | M1 |
| `query_topology` | выбор элементов запросом («плоские грани с нормалью +Z на высоте 10») → `TopoId` | M1: грани по нормали |
| `mass_properties` | объём, площадь, центр масс, габариты | M1 |
| `evaluate_variants` | параллельный расчёт N вариантов параметров на неизменяемых снимках («что если») | позже |
| `render` | PNG вида: вся модель или выбранные операции, стандартный вид (`iso`, `top`, `front`…), размер | M4b |

Ошибки перестроения структурированные: `LostReference { feature, topo_id, origin }`, `Degenerate { feature, case }` и т.д. Агент видит, что сломалось и почему, и может это исправить.

### 6.4 Ссылки на топологию

Человек или агент выбирает элемент **запросом** (`query_topology`) или кликом; в файл записывается стабильный `TopoId`. Если после перестроения элемента нет — `LostReference` с происхождением элемента, по которому можно предложить замену.

### 6.5 Слой данных (правило PoC)

Предметные данные (номер провода, наконечники, материал, обозначение, любые поля по схеме) — JSON-свойства, привязанные к стабильным идентификаторам: `FeatureId`, вхождению тела, `TopoId`. Они переживают перестроение, потому что идентификаторы стабильны.

**Свойства не входят в `content_hash` геометрии и в ключ кэша геометрических узлов.** Сменили номер провода — геометрия не пересчитывается, ранняя отсечка срабатывает сама. Зависеть от данных может только узел, который их явно читает (отчёт, трасса, у которой профиль задан типом провода).

### 6.6 Предметные пакеты (после PoC)

Ядро даёт универсальные механизмы, предметная область живёт в JSON-пакетах (концепция из CADCraft: `docs/wires.md`, `docs/reports.md`). Ядро не знает ни одного стандарта.

- **Трасса** — 3D-полилиния с радиусами изгиба и профилем: провод, кабель, жгут, труба, шланг, воздуховод — разница только в пакете данных. Длина считается из геометрии точно, плюс припуски наконечников. Тело (вытягивание профиля вдоль трассы) строится только по требованию: отображение вблизи, проверка пересечений, экспорт. Для перечней и спецификаций хватает трассы и данных.
- **Коннектор** — именованная система координат на детали (клемма, фланец, торец воздуховода). Конец трассы ссылается на «вхождение + имя коннектора» и следует за деталью как обычная зависимость графа. Тот же коннектор служит базой сопряжения деталей (обобщение iMate).
- **Схема пакета** — JSON-схема свойств и справочники (типы, наконечники, цвета), как `wires.json` в CADCraft.
- **Отчёты** — те же JSON-описания, что в CADCraft (выборка, группировка, суммы, листы, справочники). Одно описание работает на 2D-схеме и на 3D-модели; движок отчётов и ядро таблиц — крейты Datum, CADCraft их подключает (D78, D83).
- **Одна правда для схемы и 3D:** провод на схеме CADCraft и трасса в Datum — одна сущность (номер, наконечники, тип); длина из 3D приходит в перечень проводов.

## 7. Булева операция (сердце C3)

Операция **N-арная**: `Boolean(op, target, tools[])`. Массив из 10 000 вырезов — одна операция с 10 000 инструментов, а не 10 000 последовательных (последнее — O(N²) по размеру тела, именно так зависает Inventor на перфорации, PAINS P4). Массив одинаковых инструментов — одно тело `pattern_grid` с оболочкой на копию (D45); вершина каждой оболочки проверяется на вложенность. Параметр `through: [x, y, z]` растягивает инструменты вдоль направления за габарит цели, отверстие остаётся сквозным при правке толщины (D46). В PoC инструменты попарно не пересекаются; пересекающиеся — ошибка (§10). Проверка каскадом: пары с пересекающимися габаритами (BVH) → тест треугольников в `f64` с фильтром → точный пересчёт только для неразрешённых фильтром (D40).

**Элементы на развёртываемых поверхностях** (цилиндр, конус, позже листовой металл) задаются в координатах развёртки и переносятся на поверхность аналитическим изометрическим отображением (для цилиндра `u = R·θ, v = z`, с K-фактором для нейтрального слоя). Каждый элемент переносится независимо и параллельно; операций «развернуть тело → вырезать → свернуть» нет (PAINS P4). Развёртка — отдельный узел графа на том же отображении.

### 7.1 Конвейер

Так конвейер реализован (M2b–M2d). Каждый этап параллелен по данным; результаты собираются в индексированные `Vec` и сливаются в фиксированном порядке, ошибка — первая по порядку входа (`datum_brep::in_order`), поэтому тело и текст ошибки не зависят от числа потоков (C4).

1. **Подготовка:** триангуляция граней каждого тела (D38, D44) — по граням.
2. **Широкая фаза:** пары треугольников разных тел с пересекающимися габаритами — заметание по X с активным списком на тело, полосами параллельно (D45, D47).
3. **Узкая фаза:** контакт пары треугольников → концы общего отрезка (неявные точки, §7.3) и отрезки разреза граней — по парам.
4. **Слияние точек** по символьному имени (§7.2): сортируются пары «имя, номер», проверяется «одно имя — одна точка».
5. **Точки на рёбрах** упорядочиваются вдоль ребра — по рёбрам.
6. **Классификация** вершин «внутри/снаружи»: чётность пересечений вдоль рёбер, луч — только для частей без пересечений (D42). *Последовательна внутри тела.*
7. **Сборка граней:** каждая исходная грань — из сохраняемых кусков границы и отрезков разреза — по граням; циклы грани с тысячами отверстий — по циклам.
8. **Канонизация** `build`: сортировки по `TopoId` (D11), раскладка циклов, связывание рёбер, хеш Меркла (D10).

### 7.2 Символьные вершины

Вершина пересечения ребра `e` одного тела с гранью `f` другого получает ключ `(e, f)`. Её координаты вычисляются **один раз** по каноническому ключу и разделяются всеми фрагментами, которые её используют.

Следствия:
- сшивка — точное совпадение ключей, без допусков и без поиска ближайших точек;
- соседние грани, разрезанные в разных потоках, получают бит-в-бит одинаковые координаты общей вершины;
- результат не зависит от порядка вычислений.

### 7.3 Арифметика

- Координаты тел — `f64`.
- **Внутри операции работаем на треугольниках** (D38): поверхность инструмента и цели однозначна, даже если грань после поворота не точно плоская (D30), и разрез с классификацией видят одну и ту же поверхность. Триангуляция внутренняя и наружу не выходит: выходная грань собирается из фрагментов одной исходной грани одного региона, вершины на диагоналях (степени 2 между кусками одного ребра пересечения) удаляются, в ключи `TopoId` попадают только исходные грани и рёбра.
- **Точки пересечения неявные** (D38): `Lpi` — прямая ребра × плоскость треугольника, хранится как пять исходных точек. Решения о неявных точках принимают косвенные точные предикаты по исходным координатам (Cherchi, Livesu, Scateni, Attene, 2020, 2022); координаты округляются в `f64` один раз, при построении результата. Для явных точек — `robust` (адаптивная арифметика Шевчука).
- **Точная арифметика — фильтр + `num-bigint`** (D39): выражение вычисляется в `f64` с оценкой погрешности на лету; если знак не гарантирован, пересчёт в целых (каждое `f64` — целое × 2^e, после общего сдвига точно). Счётчик точных пересчётов показывает, горячий ли этот путь; свои expansions — только если бенчмарк покажет. Неявная точка хранит свои однородные координаты в арифметике фильтра, вычисленные один раз при создании: предикаты не пересобирают плоскость и прямую (D48).
- Плоскостное представление по-прежнему отклонено (D12): хранение в `f64`, неявные точки живут только внутри операции.
- **Касания — символическое возмущение** (D52): если точный знак нулевой, а среди входов есть точки инструмента, предикат пересчитывается для конфигурации, где каждая оболочка инструмента растянута от своего центра на ε и сдвинута на ε² в фиксированном общем направлении. Знак — первый ненулевой коэффициент многочлена по ε в той же обобщённой арифметике (фильтр, затем `BigInt`). Где решение пришло из возмущения, точка помечается; помеченные точки, совпадающие в точной геометрии, склеиваются, точка на чужом ребре вставляется в его цепочку, встречные куски грани и противолежащие грани нулевой толщины уничтожаются.

## 8. Детерминизм: правила для всего кода

1. Никакой итерации по `HashMap`/`HashSet` там, где порядок влияет на результат. Использовать `BTreeMap` или сортированные `Vec`.
2. Результаты параллельных этапов собираются в индексированный `Vec` и затем сортируются по ключу. Порядок завершения задач не должен влиять ни на что.
3. Параллельные редукции `f64` (суммы объёмов, площадей) — только с фиксированным деревом свёртки, не через `par_iter().sum()`.
4. Никаких счётчиков-идентификаторов, выдаваемых «кто первый взял».
5. Тест детерминизма — обязательная часть CI: каждая эталонная модель строится при 1, 4 и 16 потоках, хеши должны совпасть.

## 9. Тестирование и проверка геометрии

- **Инварианты после каждой операции** (в debug-сборке всегда): `Body::validate()`.
- **Property-based (proptest):** случайные тела в общем положении (случайные повороты на «некруглые» углы):
  - `V(A∪B) + V(A∩B) = V(A) + V(B)`;
  - `V(A−B) = V(A) − V(A∩B)`;
  - результат замкнут и многообразен.
- **Инвариантность к масштабу и положению (с M0):** та же модель, сдвинутая на 10³, 10⁶ и 10⁷ м и повёрнутая на «некруглый» угол, даёт ту же топологию (те же `TopoId`, те же числа элементов) и тот же объём с относительной точностью. Этот тест доказывает отсутствие рабочей области (принцип 8).
- **Эталонные модели** в `tests/models/*.json`; хеши каждой операции закреплены в `tests/model-hashes.json` (тест в `datum-model`; `DATUM_BLESS=1 cargo test` перезаписывает после осознанного изменения). `datum determinism-check tests/models` сравнивает результаты на 1, 4 и 16 потоках. Среди них эталоны из практики: пластина с 10 000 отверстий (`perforation.json`, P4), рельеф на регулярной сетке + котлован → объём выемки (`terrain_pit.json`, P9); те же сценарии крупнее — бенчмарки C3.
- **Внешний эталон (опционально):** скрипт на CadQuery/OCCT в WSL строит те же модели, сравниваем объём и число граней. Не в основном CI.
- Объём считается через теорему о дивергенции по граням.

## 10. Вне рамок PoC

Касания цели и инструмента (совпадающие грани, вершина на грани, ребро через ребро или вершину) решаются символическим возмущением: инструмент бесконечно мало больше (D52). Явно не поддерживается и возвращает ошибку:
- касающиеся или пересекающиеся между собой инструменты N-арной булевой операции (`Degenerate`);
- результат, который сам не многообразен: тела, соединённые только ребром или вершиной (`NonManifold`);
- невыпуклая оболочка инструмента, чья грань с внутренней стороны совпадает с гранью цели: растяжение от центра сдвигает такую грань внутрь, и остаётся кусок нулевой площади (`Degenerate`);
- нулевые толщины, самопересекающиеся контуры эскиза.

Не делается вообще: скругления и фаски, NURBS, сборки, STEP/IGES, чертежи, листовой металл.
